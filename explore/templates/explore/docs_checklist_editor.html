Checklist editor

A checklist is a form that every item of one component type carries; filling it out and pressing Submit to HWDB posts a test record on the item. The editor builds the form: a type page's Add/Edit checklists link opens it. Left, the editor and the schema JSON; right, a live preview of exactly what the fill page renders — click a field in the preview to jump to it in the editor. Save to HWDB uploads the schema onto the type; HWDB keeps every version and the newest wins, so a bad edit is always one save away from repair.

Sections

A form is a list of sections, each a titled card of fields. ▲▼ reorder, ✕ removes. Every section header on the fill page folds; start collapsed opens it folded.

Show a section only when…

The — always — select lists the checklist's select and PID fields:

  • A select field = an option: the section shows while that option is chosen. Two sections on the same field with different options give "pick H or J, then see that variant's table".
  • A PID field › a key = a value: the section shows while the scanned item's stored value at that key equals the value — read live from HWDB. A bare key such as Side reads the item's Item Specifications; serial_number or location.name read the standard fields; dots walk deeper.

A hidden section's fields are left out of the submission; values typed before switching are kept in case you switch back. A rule that matches nothing shows the section rather than hiding it.

Placing fields

Order is the layout: fields render top to bottom in editor order. Each field's placement select says where it goes relative to the field above:

PlacementResult
↵ new linebelow the field above (the default)
→ besidea new cell to the right of the field above; the row stacks on phones
↓ same cellbelow the field above, inside its cell — e.g. one step text on the left, three figure links stacked on the right

Column grid

Set columns on a section to 2–6 and every field gets col (start column, auto = next free slot), span (columns occupied, or full), new line and align (bottom, top or middle when the line is taller than the field). Fields flow left to right into the next free slot; a span that does not fit wraps. Unequal widths come from spans on a finer grid: six columns with a text spanning 3 beside three 1-wide inputs is a 3 : 1 : 1 : 1 row. On phones the grid collapses to one column in field order.

layout… opens a schematic of the grid: click a chip and move it with the arrows, change its span or alignment, drag it to a cell, drop it onto another chip to stack the two in one cell, unstack to split a stack. Every change rewrites the field order and hints.

Every field has a label; the label is the key under which the value is stored, inside its section's title ({section: {label: value}}). → Specs on a value field also writes the value into the item's Item Specifications, so it shows on the item's page — the checklist owns those sections and rewrites them wholesale at every submit.

Numbers

A number field (and every plain cell of a table) takes units and one of two ranges: nominal with ± tol, or min / max. A value outside turns red as it is typed; the submission is still accepted.

Rows

Without rows a table is one unnamed row. rows… opens a grid: the header cells hold the column syntax above, each body row has a label (unique, shown in a left cell) and one cell per column — blank means an input, text is that row's fixed text, and a range in brackets ([0 ± 0.01], [-0.01..0.01], or 3.1 [3.0..3.2] after the text) beats the column's for that row. Formula and check columns take no row text. Untouched rows are left out of the record.

Import… fills the grid from cells pasted out of a spreadsheet or a .csv file: the first line is the headers, a chosen column labels the rows (else the row number), non-empty cells become fixed text and empty ones inputs; ticking a column under User fills in blanks it. It replaces the existing columns and rows.

Looks

tint colors the cells (not the header) to match a reference drawing — yellow, green, blue, red, gray or any #rrggbb, light shades read best; a column's or a row's tint beats the table's. borders draws cell borders like a real table.

Linking table

link the cells as sub-components: every plain cell takes a PID (or a serial number resolved to one) and the items are linked into the item's free positions — by the link now button under the table or at submit; check is the dry run naming what each cell would get. into the item in position… links them into the sub-assembly sitting in that position of this item instead — the PDS module's supercell in SC1 holding eight SiPM boards, one table per supercell. Type ID and serial pattern work as on a PID field. Each row gets a 📱 that takes scans from a phone straight into its next empty cell.

Steps

One step per line. Leading spaces indent — Tab / Shift+Tab in the box, two spaces per level. Formatting applies to each line. all steps required to submit refuses Submit to HWDB until every step is ticked (a section hidden by a rule is exempt; Save draft is unaffected).

Static

Display only, in any combination:

  • Note — a paragraph of text, with formatting.
  • Reference URL — an external link, e.g. an EDMS drawing.
  • Reference image — upload a picture or a PDF drawing (stored on the type in HWDB), or type the id of one already there. It shows inline as a thumbnail that opens full size (a PDF shows its first page and opens in the PDF viewer); untick thumbnail to show the label as the link instead — a column of drawing numbers rather than pictures.
  • Link to checklist — a jump to another checklist by name: blank Type ID = this item's checklist of that name; a Type ID = that type's PID chooser. Opens in a new tab; save a draft first if half done.

On the fill page every PID field has Scan (camera), Pick (a list of the type's items, free ones for linking fields) and a phone button that shows a QR code: scanning it on a phone opens a scan page whose scans fill this field.

Plot

Embeds a Plots page for the items the form names — a Vbd distribution of the 32 boards just linked into a module. Recipe:

  1. On the sub-component type's Plots page, build the plot for one item and Copy link.
  2. Paste it as the field's Plots page URL. Only the type and the plot state are kept, so a link from another server works.
  3. Optionally name the sections and fields to read PIDs and serial numbers from (blank = every section, every field), and a serial-number pattern so only matching words count as serials.

The plot follows the form as it is filled; a section or field name the form does not have is reported under the empty box. reference plot shows the page exactly as pasted, with its own PID range, reading nothing from the form — a distribution to compare a fresh measurement with. Tolerance lines come from the Plots page's Limits boxes and travel in the link. The sub-component type's test data must have been synced on its Plots page once.

Assembly

Shows the item's positions with their occupants, read live, each PID a link, an Unlink per row and Link items → to the packing page. Nothing to fill in; the submit stores the list as it stands. the item in position… shows the positions of the sub-assembly in that position instead (the supercell in SC1).

Text formatting

Instructions, field labels, a static note and each step accept **bold**, *italic* and line breaks. HTML stays escaped. Stored keys are the raw text, markers included. The fill page and the preview carry an A− / A+ / ↺ control that scales the whole checklist's text; the choice is remembered per device.

Schema JSON

The JSON pane mirrors the editor as you work. Hand-edit or paste a schema and press Apply JSON to the editor. The shape:

{
  "name": "Reception",
  "test_type_name": "Reception",
  "instructions": "Unpack, inspect, measure.",
  "sections": [
    {"title": "Identification", "fields": [
      {"type": "qr", "label": "Batch PID", "type_id": "D00300100002"},
      {"type": "number", "label": "Thickness", "units": "mm",
       "nominal": 1.6, "tol": 0.1, "to_spec": true}
    ]},
    {"title": "Measurements", "grid": 4, "fields": [
      {"type": "table", "label": "Resistance", "span": "full",
       "columns": ["P1", "P2", "Mean = (C1 + C2) / 2 [10 ± 1]"]},
      {"type": "steps", "label": "Procedure", "require_all": true,
       "steps": ["Power on", "  Wait 5 min", "Record"]}
    ]}
  ]
}

Unknown types and malformed entries are dropped silently on render. The templates in Start from are the format reference.

On the fill page

  • Submit to HWDB posts, in order: photos to the item, links into sub-components, → Specs values, then one test record of the checklist's test type with {section: {label: value}}. The latest submission pre-fills the next visit.
  • Save draft keeps the values server-side per item, checklist and user; the browser also autosaves every change on the device. Save CSV / Load CSV work offline; Print gives a procedure sheet; Email opens a mail draft.
  • A page opened once online comes back offline, with its drawings. Submitting is online-only.
  • The type page lists the checklists; each opens a PID chooser (scan, type, or click an item), with + New item to mint an item first and land in the checklist.
